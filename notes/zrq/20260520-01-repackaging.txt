==START==
Regarding the project at `/calycopis/Calycopis-broker/github-zrq`.
Recent changes to this project have been working towards separating out the Spring specific
parts of the code from the core business logic.
Gradually moving the Spring specific parts into the `net.ivoa.calycopis.broker.spring` package,
leaving the framework neutral business logic in the `net.ivoa.calycopis.broker.engine` package.
Part of this work has been to wrap the Spring specific JpaRepository references using
the `SpringAbstractEntityRepository` repository interface and `SpringAbstractEntityRepositoryWrapper`
which implements a framework neutral `AbstractEntityRepository` interface that can be used in
the rest of the business logic.

Can you identify what is causing the following runtime error:
```
2026-05-20 10:15:59 WARN main AnnotationConfigServletWebServerApplicationContext refresh()
    Exception encountered during context initialization - cancelling refresh attempt:
    org.springframework.beans.factory.UnsatisfiedDependencyException:
    Error creating bean with name 'dockerPlatformImpl':
    Unsatisfied dependency expressed through field 'springAbstractComputeResourceEntityRepository':
        Error creating bean with name 'springAbstractEntityRepository' defined in net.ivoa.calycopis.broker.spring.SpringAbstractEntityRepository
            defined in @EnableJpaRepositories declared on AmbleckApplication:
                Not a managed type: class java.lang.Object
```
==END==

--START--
....
....
  The problem is in SpringAbstractEntityRepository. It's a generic interface annotated with @Repository that extends JpaRepository<EntityType, UUID>:

   /calycopis/Calycopis-broker/github-zrq/java/src/main/java/net/ivoa/calycopis/broker/spring/SpringAbstractEntityRepository.java lines 35-38

  @Repository
  public interface SpringAbstractEntityRepository<EntityType>
  extends JpaRepository<EntityType, UUID>
      {

  Because AmbleckApplication has @EnableJpaRepositories("net.ivoa.calycopis"), Spring Data JPA scans the package and finds SpringAbstractEntityRepository. It tries to create a repository
   proxy bean for it directly. Due to Java type erasure, the unbound type parameter EntityType resolves to Object at runtime. Spring then checks whether Object is a JPA managed entity —
  it isn't — and you get the error: "Not a managed type: class java.lang.Object".

  The concrete subinterface SpringSessionEntityRepository works fine because it binds the type parameter to a real entity class:

   /calycopis/Calycopis-broker/github-zrq/java/src/main/java/net/ivoa/calycopis/broker/spring/SpringSessionEntityRepository.java lines 35-37

  @Repository
  public interface SpringSessionEntityRepository
  extends SpringAbstractEntityRepository<SimpleExecutionSessionEntity>

  The fix: Add @NoRepositoryBean to SpringAbstractEntityRepository to tell Spring Data JPA it's a base interface and should not be instantiated directly:

  import org.springframework.data.repository.NoRepositoryBean;
  @NoRepositoryBean
  public interface SpringAbstractEntityRepository<EntityType>
  extends JpaRepository<EntityType, UUID>

  However, this alone won't fully solve the problem. In DockerPlatformImpl, you're @Autowired-injecting generic parameterizations of SpringAbstractEntityRepository directly (e.g.
  SpringAbstractEntityRepository<AbstractComputeResourceEntity>). With @NoRepositoryBean, Spring won't create proxies for the generic base, so those injections will have no bean to
  satisfy them.

  You'll need to create concrete sub-interfaces for each entity type, following the same pattern as SpringSessionEntityRepository. For example:

  @Repository
  public interface SpringComputeResourceEntityRepository
  extends SpringAbstractEntityRepository<AbstractComputeResourceEntity> {}
  @Repository
  public interface SpringDataResourceEntityRepository
  extends SpringAbstractEntityRepository<AbstractDataResourceEntity> {}
  @Repository
  public interface SpringExecutableEntityRepository
  extends SpringAbstractEntityRepository<AbstractExecutableEntity> {}
  @Repository
  public interface SpringStorageResourceEntityRepository
  extends SpringAbstractEntityRepository<AbstractStorageResourceEntity> {}
  @Repository
  public interface SpringVolumeMountEntityRepository
  extends SpringAbstractEntityRepository<AbstractVolumeMountEntity> {}

  Then update the @Autowired fields in DockerPlatformImpl (and MockPlatformImpl) to reference these concrete types instead of the generic SpringAbstractEntityRepository<...>.
--END--

Before we implment this, can you analyse what happens to the database connections and transactions during an iteration of the loop() method.
==END==

--START--
  Good question. Let me trace through the transaction and connection lifecycle for a single iteration of loop().

  The loop() method itself has no @Transactional annotation, and is invoked by @Scheduled(fixedDelay = 1000) on TestProcessingSerivceImpl, which also doesn't start a transaction. So there
  is no ambient transaction wrapping the loop.

  Each iteration goes through four distinct phases:

  ────────────────────────────────────────

  Phase 1: inner.getNext(this) -- @Transactional(propagation = Propagation.REQUIRES_NEW)

  • Spring acquires a database connection from the pool and opens a new transaction.
  • Executes selectNextRequest() -- a JPQL query looking for a request already claimed by this service.
  • If none found, executes updateNextRequest() -- a @Modifying JPQL UPDATE that atomically claims the next unclaimed request by setting its service column to this service's UUID.
  • If a row was claimed, executes selectNextRequest() again to retrieve the claimed request's UUID.
  • Transaction commits, connection returned to the pool.
  • Returns the UUID (or null if no work available).

  ────────────────────────────────────────

  Phase 2: inner.preProcess(this, requestId) -- @Transactional(propagation = Propagation.REQUIRES_NEW)

  • Spring acquires a connection and opens a new, independent transaction.
  • requestRepository.findById(requestId).orElseThrow() -- loads a fresh ProcessingRequestEntity from the database. This entity is managed within this transaction's persistence context.
  • Calls back to outer.preProcess(request), which calls request.preProcess(platform). This is where the business logic determines what action to take. Any lazy-loaded associations on
    the entity are fetched within this transaction.
  • Returns a ProcessingAction object (a plain Java object, not an entity).
  • Transaction commits, connection returned to pool. The ProcessingRequestEntity becomes detached.

  ────────────────────────────────────────

  Phase 3: action.process() -- No transaction, no connection

  • Runs entirely outside any database transaction. No connection is held.
  • This is the potentially long-running external work (e.g., Docker container operations, HTTP calls).
  • This is intentional by design -- the ProcessingAction javadoc says: "An external action that is performed outside of any database transactions. This means that the action may take a
    non-trivial amount of time without locking up the database."

  ────────────────────────────────────────

  Phase 4: inner.postProcess(this, requestId, action) -- @Transactional(propagation = Propagation.REQUIRES_NEW)

  • Spring acquires a connection and opens a new, independent transaction.
  • requestRepository.findById(requestId).orElseThrow() -- reloads the entity fresh from the database (not reusing the detached instance from Phase 2).
  • Calls back to outer.postProcess(request, action), which calls request.postProcess(platform, action) -- updates entity state based on the action result.
  • request.setService(null) -- releases ownership of the request so it won't be picked up by selectNextRequest again for this service.
  • Transaction commits (dirty-checking flushes the entity changes), connection returned to pool.

  ────────────────────────────────────────

  Key observations:

  1. Three independent transactions per iteration -- each using REQUIRES_NEW, so they are completely isolated from each other. A failure in Phase 4 does not roll back Phase 2's commit.

  2. No connection held across the loop iteration -- connections are acquired and released within each transactional method. During action.process() (Phase 3), no database connection is
     held at all.

  3. Entity is reloaded fresh in each transaction -- Phase 2 and Phase 4 both do findById(), avoiding detached entity problems. The entity from Phase 2 is not carried into Phase 4.

  4. Single-threaded -- the loop is sequential, so at most one connection is held at any time.

  5. Claim-then-load pattern in getNext() -- the updateNextRequest() uses a subquery with LIMIT 1 to atomically claim a request, avoiding race conditions between concurrent service
     instances.

  6. Regarding the planned refactoring -- the transaction boundaries are entirely defined by the @Transactional(propagation = Propagation.REQUIRES_NEW) annotations on the inner class
     methods. When these move to SpringProcessingTransactionHandlerImpl, the transaction behavior will be preserved identically, since the new class will be a @Service bean and Spring's
     transaction proxy will apply the same way.
