  Calycopis - Execution Broker Prototype

  This is a Java/Spring Boot project implementing the IVOA Execution Broker service. The broker provides a common API abstraction
  over different execution platforms (OpenStack, Docker, Kubernetes, Slurm, etc.).

  Key concepts:
  • Offer sets — clients submit execution requests and get back offers for execution sessions
  • Execution sessions — concrete instances of running executions
  • Resources — executables (Docker, Singularity, Jupyter), compute, storage, volumes, and data resources
  • Lifecycle — rich state machines (OFFERED → ACCEPTED → PREPARING → RUNNING → COMPLETED, etc.)

  Architecture highlights:
  • Three-tier Entity/Factory/Validator/Repository pattern (Abstract → Simple → Mock/Docker)
  • Polymorphism via discriminators for all domain types
  • Chain-of-responsibility validation pipeline
  • OpenAPI schema lives in a sibling project at /calycopis/Calycopis-schema/github-zrq/
  • PostgreSQL required (no H2 support)
  • Runs inside a developer-tools Fedora container with Podman socket bind-mounted for container-in-container execution

  Coding conventions to follow:
  • No ternary ?: operators (except in logging) — use expanded if/else
  • Prefer JPA annotations over Spring-specific ones
  • Avoid fragile patterns (@Transient + initEntity(), static singletons, ApplicationContextAware, etc.)
  • GPL license headers on all source files
  • AIMetrics blocks in file headers
  • Copyright year must be current year

  Project structure:
  • java/ — main source code
  • docker/ — container definitions
  • tests/ — curl, Java, and Python tests
  • agents/ — coding rule files (license headers, copyright, AI metrics)
  • Two platform profiles: mock and docker

  The file has been created at /calycopis/Calycopis-broker/ivoa-wiki/Resource-starvation.md. Here's a summary of what it covers:

  Four starvation scenarios:

  1. Phantom reservation — OFFERED sessions consume booking capacity (confirmed in the ComputeResourceOfferFactoryImpl query which
     counts OFFERED phases). If users request offers but don't accept them, resources are blocked until expiry.

  2. Popular data stampede — A burst of concurrent requests for the same dataset can all receive offers based on the same stale
     capacity snapshot, overcommitting a single platform before the load-balancing feedback loop kicks in.

  3. Long-running task blocking — A small number of long-duration tasks (e.g. ML training) can lock out shorter interactive sessions
     for extended periods.

  4. Cascading congestion — When system-wide demand exceeds supply, overflow from one platform saturates the next in a chain
     reaction.

  Mitigations grouped into three categories:

  • Offer lifecycle controls — short expiry times (using the existing expires schema field), limits on outstanding offers per user,
    admission control
  • Capacity management — pessimistic estimation, resource partitioning, duration limits (the codebase already has MAXIMUM_DURATION),
    queue depth caps
  • Policy-based steering — administrative weighting (linking back to Load-balancing.md), per-user quotas, and the NO result on
    OfferSetResponse

  The closing point emphasises that all mitigations are implementable as platform-local policies without changes to the core protocol —
   consistent with the project's design philosophy.
