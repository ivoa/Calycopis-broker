==START==
/plan
The following task relates to two projects, an OpenAPI specification at `/calycopis/Calycopis-schema/github-zrq`
and a Java web-service implementation at `/calycopis/Calycopis-broker/github-zrq`.
Start by reading the AGENTS.md files for both projects.
Then consider the following task.
At the moment the web service does not have any support for authentication or authorization.
Can you create a plan to implement authentication and authorization based on the following criteria:
* Authentication using both OpenID Connect (OIDC) using an external identify provider and username/password in the local database.
* An authenticated identity maps to an Identity interface and IdentityEntity class.
* The Identity interface extenmds Component and the IdentityEntity class extends ComponentEntity.
* The identity for an inbound request should be resolved by the web service layer and passed as a parameter to the factory method handling the request.
* All ComponentEntity entities are assigned an 'owner' property that links to the IdentityEntity that created them.
* An IdentityEntity instance references itself as its 'owner'
==END==

  Good question. The answer depends on how much of the identity model you want exposed through the API. There are three potential areas of schema impact:

  1. Security schemes (documentation-only)

  The OpenAPI spec currently has no securitySchemes defined. Adding them would document the supported auth mechanisms for clients:

  securitySchemes:
    bearer:
      type: http
      scheme: bearer
      bearerFormat: JWT
    basic:
      type: http
      scheme: basic

  This is not required for the implementation to work (Spring Security operates independently of the spec), but it's good practice for client generation
  and documentation.

  2. Owner field in ComponentMetadata

  If you want the owner of a component to be visible in API responses (e.g., "who created this session?"), then ComponentMetadata in the schema would need
   a new field — something like:

  owner:
    type: string
    format: uri
    description: URL of the identity that owns this component

  If the owner is purely internal (for server-side authorization checks only and never serialised to clients), then no schema change is needed here.

  3. Identity as an API resource

  If identities should be queryable via a new endpoint (e.g., GET /identities/{uuid} or GET /identities/whoami), that would require a new path and
  response type in the schema.

  ────────────────────────────────────────

  In the current plan as written, the Identity model is server-side only — it's used internally for ownership tracking and authorization. The
  makeBean(URIBuilder) serialisation methods on entities wouldn't include owner information unless the schema is updated.

  So the key question is: do you want the owner/identity to be visible in API responses, or is it purely for internal authorization? That determines
  whether the schema project needs changes.

  There are two distinct aspects to consider:

  1. The generated Python client classes themselves

  If the OpenAPI schema is not changed (identity stays internal), then the generated client classes do not need to be regenerated. They remain as-is.

  Even if you later add securitySchemes to the schema and regenerate, OpenAPI Generator's Python clients typically already include authentication hooks in
   the Configuration class (fields for access_token, username, password, API key headers, etc.) regardless of whether the schema declares security
  schemes. So regeneration would be a cosmetic/documentation improvement, not a breaking change.

  2. The Python test code that uses the client

  This is where changes are required. Once security enforcement is enabled (Phase D), the tests must provide credentials with their requests. Typically
  this means configuring the client like:

  # For Basic auth (local account)
  configuration = Configuration(
      host="http://localhost:8082",
      username="testuser",
      password="testpass"
  )
  # For Bearer/OIDC token
  configuration = Configuration(
      host="http://localhost:8082",
      access_token="eyJhbG..."
  )

  The tests would also need a setup step to either:
  • Create a local test identity (e.g., via a management endpoint or direct DB insertion)
  • Or obtain a token from the OIDC provider

  ────────────────────────────────────────

  Summary: The generated client library itself should work without regeneration. The test scripts would need modifications to pass authentication
  credentials, but this can be deferred to Phase D. During Phases A-C (with security permissive), existing tests continue to pass unchanged.
