# metrics

    #
    # Simple form
    # `kind` identifies the meaning and structure of the metric

    metrics:
      - kind: uri:example-metric - extends min-max-float-metric
        min: float
        max: float

    Clients/services that don't understand the kind reject the message.

    #
    # Separate the structure from the meaning.
    # `kind` identifies the strcture
    # `metric` identifies the meaning of metric

    metrics:
      - kind: uri:min-max-float-metric
        metric: uri:example-metric
        min: float
        max: float

    Clients/services that don't understand the structure (kind) reject the message.
    Clients/services that don't understand the meaning (metric) can choose whether they reject the message or not.
    Does this actually provide any benefit ?

        It allows a 3rd party to add a new type of metric (meaning) without having to define it in a schema.

    If a service doesn't understand the type of metric (meaning), then it can't know whether it can ignore it or not.
    Unless we add an 'optional' flag.

    Does this actually provide any benefit ?

        Not really. If a metric is optional, don't include it in the request.

    If a service offers a metric that the client doesn't understand, then we don't want the client to reject it.
    Does this actually provide any benefit ?

        Yes. A service can list all of the metrics that it has and the client can decide which ones to take notice of.

    Do we want to get into AND/OR combinations at this point - probably not.
    Assume all metrics are AND for now.

    metrics:
      - kind: uri:min-max-float-metric
        metric: uri:example-metric-one
        min: float
        max: float
      - kind: uri:min-max-float-metric
        metric: uri:example-metric-two
        min: float
        max: float

# 402 redirect
# https://www.x402.org/

    Add 'payment-required' redirect.
    Headers:
        location: https://payment.service.endpoint/....
        x-ivoa-payment-kind: uri:uksrc-carbon-payment

    #
    # Growing ecosystem of payment handling platforms.
    # https://www.x402.org/ecosystem

    Benfits:
    * Client to specify maximum payment they are offering (bid)
    * Service can specify min and max cost (ask) before the job is executed.
    * User (or agent) chooses to accept the offer.
    * Updating to ACCEPTED can return 402 redirect if not already paid.
